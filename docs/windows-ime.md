# Windows 最小化恢复后的输入法候选窗口错位

现象：使用微软拼音时，NextChat 从最小化状态恢复后，输入框看起来已有焦点，但中文候选或组合窗口偶发地出现在应用外。手动让输入框失焦再聚焦可以恢复。

疑似原因是 WebView2 的原生文本输入上下文或光标坐标在恢复窗口时没有同步恢复。目前没有本项目的故障现场事件记录，不能确认底层原因。相关上游报告：

- [Tauri #16391](https://github.com/tauri-apps/tauri/issues/16391)：相同 Tauri/Wry 版本在窗口切换后出现 IME 位置异常；触发场景与本项目不完全相同。
- [WebView2 #5675](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5675)：调整宿主窗口大小后，组合窗口出现在屏幕左上角。

## 应用侧兼容处理

`app/utils/windows-ime.ts` 在 Windows Tauri 客户端监听原生窗口焦点变化。窗口重新获得焦点后，等待两次 animation frame，让窗口有机会恢复布局；如果原先聚焦的文本框仍然聚焦，则执行一次同步的 `blur()` / `focus({ preventScroll: true })`，并保留草稿、选区方向和输入框滚动位置。

这是利用用户已观察到的恢复方式做的兼容处理，不代表上游缺陷已经修复。

- 仅处理 textarea 和 text/search/url/tel 输入框。
- 用户在等待期间点击、输入或开始中文组合输入时，取消刷新。
- 中文组合输入未结束、窗口仍在后台、控件已移除或禁用、焦点已改变时，不刷新。
- 不主动把焦点从按钮或其他控件移到聊天框。
- 失焦处理器如果转移焦点或移除控件，会中止后续恢复。
- `blur`/`focus` 会触发页面对应事件，因此带有自定义失焦行为的文本框需要手工回归。

## 验证

自动检查：`yarn test:ci --runInBand test/windows-ime.test.ts test/window-size.test.tsx`、`yarn typecheck`。JSDOM 测试验证焦点恢复逻辑和保护条件，不模拟 Windows TSF 或原生候选窗口。

Windows 真机回归需使用包含该改动的客户端：

1. 使用微软拼音，在聊天框输入草稿，设置非末尾的光标或反向选区。
2. 最小化，再从任务栏恢复，直接输入中文；重复至少 20 次，观察候选位置以及草稿、选区是否保持。
3. 用 Alt+Tab 切出再切回，重复上述检查。
4. 恢复窗口后立即打字、点击另一个输入框或切换会话，确认没有焦点被抢回、漏字或重复输入。
5. 在有未提交拼音时切出再切回，确认兼容处理不会额外提交或取消组合输入。
6. 检查侧栏搜索、设置及弹窗文本框，确认失焦事件没有导致异常保存或关闭。

如果仍然错位，应收集故障时原生窗口焦点、DOM 焦点、composition 事件和控件坐标的顺序，再判断是否需要原生 WebView2 层处理；不要直接增加反复定时聚焦。
